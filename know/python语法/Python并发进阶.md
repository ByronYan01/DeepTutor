# Python 并发编程进阶指南（面向前端开发者）

> 本文从 Web 前端（JavaScript/Node.js）开发者的视角出发，用 JS 中熟悉的概念来理解 Python 的三种并发模型，以及它们之间的协调机制。

## 1. 核心概念速查表

| Python 技术 | JS 对等物 | 针对问题 | 关键特征 |
| :--- | :--- | :--- | :--- |
| **协程 (asyncio)** | Event Loop + async/await | 网络 I/O 等待 | 单线程切换任务，极低消耗 |
| **多线程 (threading)** | Web Worker（但共享内存） | 磁盘 I/O / 同步阻塞库 | 共享内存，受 GIL 锁限制 |
| **多进程 (multiprocessing)** | Chrome 多标签页 / Node cluster | CPU 计算密集 | 独立资源，真正并行 |

---

## 2. 协程 (Asyncio) = JS 的事件循环

### 原理

Python 的 `asyncio` 和 JS 的事件循环本质上是**同一个东西**：在**一个进程**的**一个线程**里，通过事件循环不断轮询任务。

```
事件循环不断在做同一件事（无限循环）：
  ① 有没有就绪的任务？→ 有 → 执行它，直到它遇到 await（IO等待）
  ② 有没有 IO 完成了？→ 有 → 唤醒对应的任务，放入就绪队列
  ③ 回到 ①
```

### JS 与 Python 对照

| 概念 | JavaScript | Python |
| :--- | :--- | :--- |
| 异步对象 | `Promise` | `Future` / `Task` |
| 执行关键字 | `await` | `await` |
| 并发等待 | `Promise.all([...])` | `asyncio.gather(...)` |
| 底层核心 | Event Loop (libuv) | Event Loop (asyncio) |
| 是否默认启动 | ✅ 天生就有 | ❌ 需手动启动（`asyncio.run()` 或 FastAPI 帮你启动） |

### 比喻：银行柜台（自觉排队模式）

银行只有一个柜员（CPU），100 个客户（100 个用户请求）同时到来：

- **没有协程（纯同步）**：柜员给客户 1 办业务 → 客户 1 等数据库返回（3 秒）→ 柜员傻等 3 秒 → 办完 → 接下来客户 2 ... 100 个客户排完要 300 秒。
- **有协程**：柜员给客户 1 办 → 客户 1 说"我要等数据库"(`await`) → 客户 1 自觉去旁边坐着 → 柜员立刻给客户 2 办 → 客户 2 也在等 API → 也去旁边坐 → ... → 客户 1 的数据库回来了 → 柜员回来继续给客户 1 办。

> [!IMPORTANT]
> **协程不会让"一个人的事情变快"**，而是让柜员不会因为一个人的等待而闲着。对于单个任务内部，`await` 就是在同步等待。并发的好处体现在**多个用户同时请求服务器**时。

### 协程的致命弱点：同步阻塞

协程是**协作式调度**——只有代码执行到 `await` 时才会让出执行权。如果一个协程内部跑了一个同步阻塞操作（比如 PyMuPDF 解析 PDF、或一个不带 `await` 的 `while` 循环），它就**永远不会让出执行权**，事件循环被彻底卡住，所有其他协程都得不到执行机会。

用银行比喻来说：客户 A 是个「不自觉」的人——他不去旁边坐着等，而是一直站在窗口不走（同步阻塞）。柜员只能一直伺候他，后面 99 个客户全部干等。

**这就是为什么需要多线程来处理同步阻塞任务。**

### 并发请求 = `Promise.all`

如果你需要同时从多个地方拿数据，可以使用 `asyncio.gather`（等价于 JS 的 `Promise.all`）：

```python
# Python 版 "Promise.all"
db_result, api_result, local_result = await asyncio.gather(
    query_db(query),       # 同时发起
    fetch_api(query),      # 同时发起
    search_local(query)    # 同时发起
)
# 总时间 = max(各请求时间)，而不是相加
```

```javascript
// JS 等价写法
const [dbResult, apiResult, localResult] = await Promise.all([
    queryDb(query),
    fetchApi(query),
    searchLocal(query)
]);
```

### 项目中的实际应用

DeepTutor 使用 FastAPI 作为 Web 框架。FastAPI 本身就是基于 asyncio 事件循环运行的。当用户 A 在等待 Embedding API 返回向量时，事件循环会去处理用户 B 发来的新消息。

## 3. 多线程 (Threading) = 增强版 Web Worker

### 为什么 Python 需要多线程，而 JS 不太需要？

**JS 世界**：几乎所有库都是异步的（`fetch`、数据库驱动全部返回 Promise），你很少遇到"一个函数调了就卡住整个页面"的情况。

**Python 世界**：大量老牌库是**同步的**（PyMuPDF、scikit-learn 等）。它们一旦开始执行，就像一个 `while(true)` 死循环一样霸占着主线程。多线程的存在就是为了**把这些"霸道"的同步库丢到后台线程去跑**。

### JS 与 Python 对照

| | JS Web Worker | Python 多线程 |
| :--- | :--- | :--- |
| 内存是否共享 | ❌ 不共享，必须用 `postMessage` 传数据 | ✅ **共享**，所有线程直接读写同一个变量 |
| 能否操作主逻辑 | ❌ 不能操作 DOM | ✅ 能直接访问主线程的所有数据 |
| 真正并行计算 | ✅ 真并行 | ❌ 受 GIL 限制，CPU 计算不能真并行 |

### GIL（全局解释器锁）是什么？

Python（CPython 解释器）的一个设计：**在一个进程内，同一时刻只允许一个线程执行 Python 字节码**。

想象 GIL 就是一个**只有一个麦克风的会议室**——谁拿着麦克风谁才能说话（执行 Python 代码），其他人只能等。

### 比喻：银行柜台（前台经理查岗模式）

柜员依然只有一个，但银行设了个"前台经理"（Python 解释器）。他拿着秒表，规定：每个人只能在窗口站一小段时间。
- 即使客户 A 在窗口解析一个超大的 PDF，时间一到，经理吹哨："时间到！A 你去后面排着，B 你上！"
- 尽管 A 不乐意，他也被**强行**换下（这叫"抢占式调度"）。

### 项目中的实际应用

在 `llamaindex.py` 中，LlamaIndex 的索引构建函数是同步阻塞的。如果直接在 asyncio 事件循环中调用，会导致整个服务器卡死。所以用 `run_in_executor` 把它丢到后台线程：

```python
# Python 的 run_in_executor ≈ JS 的 new Worker()，但更方便
loop = asyncio.get_event_loop()
index = await loop.run_in_executor(
    None,  # 使用默认线程池
    lambda: VectorStoreIndex.from_documents(documents)  # 在后台线程跑
)
# 后台线程跑完了，主线程拿到结果，继续处理
```

## 4. 多进程 (Multiprocessing) = Chrome 多标签页

### 原理

开启**多个独立的进程**，每个进程有自己完整的 Python 解释器和 GIL 锁，可以在不同的 CPU 核心上**真正同时计算**。

### JS 与 Python 对照

| | Chrome 多标签页 / Node cluster | Python 多进程 |
| :--- | :--- | :--- |
| 内存 | 每个标签页/进程有独立的内存 | 每个进程有独立的内存和解释器 |
| 崩溃隔离 | 一个标签页崩了，其他没事 | 一个子进程挂了，主进程没事 |
| 数据通信 | 不能直接访问对方变量 | 需要通过"管道"传数据 |
| CPU 利用 | 可以跑在不同的 CPU 核心上 | ✅ 真正的物理并行 |

### 比喻：银行开分店

总行发现一家银行排队太长，直接在隔壁又开了 3 家一模一样的分店。每个分店都有自己完整的窗口、柜员和经理，4 个客户可以**真正同时**办业务。代价是要付 4 份房租（4 倍内存消耗）。

### 前端开发中你已经接触过的"多进程"思想

1. `npm run build` 时，Webpack/Vite 用多个 worker 进程并行编译不同的文件。
2. Node.js 的 `cluster` 模块：开 4 个 Node 进程监听同一个端口，分摊流量。

### 代码示例

```python
from concurrent.futures import ProcessPoolExecutor

# 开 4 个子进程，真正同时计算
with ProcessPoolExecutor(max_workers=4) as pool:
    results = list(pool.map(heavy_computation, datasets))
```

> [!NOTE]
> DeepTutor 项目目前没有使用多进程，因为瓶颈在**等 API 返回**（等 LLM 生成、等 Embedding 接口），而不是 CPU 计算。用协程 + 线程池已经完全够用。

## 5. 什么是 I/O？

I/O 是 **Input/Output（输入/输出）** 的缩写，指 CPU 与外部设备之间交换数据的操作。核心特征是：**CPU 在等别人，自己很闲**。

| 类别 | 具体例子 | 在等什么 |
| :--- | :--- | :--- |
| **磁盘 I/O** | 读写文件、本地 SQLite | 等硬盘响应 |
| **网络 I/O** | HTTP 请求、调用 API、远程数据库查询 | 等网络传输 |
| **用户 I/O** | `input()` 等待键盘输入 | 等用户操作 |
| **设备 I/O** | 摄像头、打印机、串口 | 等硬件响应 |

与之对比，**CPU 计算**（`for` 循环、矩阵运算、排序）是 CPU 自己在干活，很忙。

在 DeepTutor 项目中，常见的 I/O 操作包括：调用 LLM API、获取 Embedding 向量、读取 PDF 文件、读写向量数据库——这些占了运行时间的绝大部分。

## 6. 线程调度 vs 协程调度

虽然多线程（GIL 下）和协程看起来都是"轮流干活"，但它们的调度方式完全不同：

| | 协程（协作式） | 多线程（抢占式） |
| :--- | :--- | :--- |
| **谁说了算** | **代码自己**，只有写了 `await` 才让出 | **Python 解释器/操作系统**，强制切换 |
| **风险** | 如果没有 `await` 的死循环，整个程序卡死 | "强行换人"可能导致数据竞争，需要加锁 |
| **效率** | 极高，没有上下文切换开销 | 较低，线程切换有额外成本 |
| **适用** | 所有库都支持 async 的场景 | 老库不支持 async，需要后台执行 |

### `await` 让出 vs GIL 释放的关键区别

两者都是"让出执行权给别人"，但让出之后自己的状态完全不同：

**协程 `await` = 我停下来等，让你先跑（串行切换）**

```
协程A: [执行代码] → await fetch_api() → [完全暂停，什么都不干] → [API返回，恢复执行]
协程B:                                   [获得执行权，开始跑]

时间线: ──A在跑──→──B在跑──→──A继续──→     ← 始终只有一个在跑
```

协程 `await` 后彻底暂停，CPU 完全交给别人。

**线程释放 GIL = 我不需要麦克风了，你拿去用，但我在旁边继续干自己的活（真正并行）**

```
后台线程: [Python代码] → 调用C扩展/I/O → [释放GIL，但自己还在跑C代码！] → [完成，重新获取GIL]
主线程:                                  [拿到GIL，执行Python代码]

时间线: ──后台线程在跑──→──两个线程同时在跑！──→   ← 真正的并行
```

用银行比喻：
- **协程 `await`** = 客户 A 对柜员说"我等转账到账"，然后**去旁边坐着发呆**（完全空闲），柜员服务下一个人
- **线程释放 GIL** = 客户 A 对柜员说"我不需要你了"，然后**去旁边桌子上奋笔疾书填表**（还在干活），柜员同时服务下一个人——**两个人同时在工作**

## 7. 深入理解：主线程、后台线程与事件循环的协调机制

> [!IMPORTANT]
> 这一节是核心中的核心。理解了这部分，就理解了 Python 异步 + 多线程混合使用的完整图景。

### 全局架构

```
┌────────────────────────────────────────────────────────────┐
│                      操作系统 (最底层)                       │
│  负责：时间片轮转，强制切换线程，分配 CPU 时间                  │
├────────────────────────────────────────────────────────────┤
│                     GIL (Python 层)                        │
│  负责：保证同一时刻只有一个线程能执行 Python 字节码              │
│  切换时机：每 ~5ms 检查一次 / I/O 时主动释放                   │
├──────────────────────┬─────────────────────────────────────┤
│      主线程           │        后台线程（一个或多个）           │
│  ┌─────────────┐     │    ┌──────────────────┐             │
│  │  事件循环     │     │    │  同步阻塞任务      │             │
│  │  协程A       │     │    │  (PDF解析/索引构建) │             │
│  │  协程B       │     │    │  由 OS+GIL 调度    │             │
│  │  协程C       │     │    │  不需要 await      │             │
│  │  (await切换)  │     │    └──────────────────┘             │
│  └─────────────┘     │                                     │
└──────────────────────┴─────────────────────────────────────┘
```

**只有主线程有事件循环**，后台线程没有。后台线程就是纯粹的线程，靠操作系统和 GIL 来调度。

### 两层调度如何配合

GIL 就像一把钥匙在多个线程之间流转，通过两种方式传递：

**方式1：被动让出（5ms 超时强切）**
```
线程A 执行纯 Python 代码 → 5ms 到了 → 解释器强制让出 GIL
→ 所有等待的线程竞争 GIL → 某个线程抢到，开始执行
```

**方式2：主动让出（I/O / C扩展）**
```
线程B 遇到磁盘读取 → 主动释放 GIL（但线程B仍在等I/O）
→ 其他线程竞争 GIL
→ 线程B 的 I/O 完成后，重新加入竞争队列等着拿回 GIL
```

主线程也不是"特权线程"，它在 GIL 面前和后台线程**平等竞争**。主线程的事件循环里所有协程都在 `await` 时，事件循环没事可干，也会主动让出 GIL 给后台线程。

### 主线程与后台线程能同时跑吗？

- **执行纯 Python 代码时**：❌ 不能，GIL 限制交替执行
- **后台线程在执行 I/O 或 C 扩展代码时**：✅ 可以！因为 GIL 被释放了

| 后台线程在做什么 | 是否释放 GIL | 能否与主线程真正并行 |
| :--- | :--- | :--- |
| 纯 Python 计算（`for` 循环） | ❌ 不释放 | ❌ 交替执行 |
| 磁盘 I/O（`file.read()`） | ✅ 释放 | ✅ 真正并行 |
| 网络 I/O（`socket.recv()`） | ✅ 释放 | ✅ 真正并行 |
| C 扩展库（NumPy/PyMuPDF） | ✅ 释放 | ✅ 真正并行 |

实际项目中，大多数耗时操作（网络请求、文件读写、C 库计算）都会释放 GIL，所以 `run_in_executor` 的效果在实践中 ≈ 真正的并行。

> [!TIP]
> 这也是为什么 **"多线程对 I/O 密集型任务有效，对 CPU 密集型任务无效"**——I/O 时 GIL 释放了能真正并行，纯 Python CPU 计算时 GIL 不释放只能交替跑。如果真的需要 CPU 并行，就得用**多进程**，每个进程有自己的 GIL，互不影响。

### `run_in_executor` 的完整生命周期

`run_in_executor` 是连接事件循环和后台线程的桥梁。它不是"轮询检查"后台线程状态，而是**通知机制**：

```
第1步 — 事件循环创建任务（主线程）：
  loop.run_in_executor(None, sync_function)
    → 创建一个 Future 对象（类似 JS 的 Promise）
    → 把 sync_function 提交给线程池
    → 当前协程遇到 await，挂起自己
    → 事件循环去处理其他协程

第2步 — 后台线程执行任务（独立于事件循环）：
  线程池中的某个线程执行 sync_function
    → 竞争 GIL → 执行 → 遇到 I/O 释放 GIL → ...
    → 执行完毕，设置 Future 的结果
    → 通过 loop.call_soon_threadsafe() 通知事件循环

第3步 — 事件循环收到通知，唤醒协程（主线程）：
  事件循环在下一轮轮询时发现通知：
    → 唤醒之前 await 的协程
    → 把结果交给协程，协程继续执行
```

注意第2步结束时，后台线程是**主动通知**事件循环的，而不是事件循环不停地去问"好了没？"。这和 JS 中 Web Worker 通过 `postMessage` 通知主线程是同一个模式：

| | JavaScript | Python |
| :--- | :--- | :--- |
| 异步包装对象 | `Promise` | `Future` |
| 实际执行 | Web Worker | 后台线程 |
| 完成通知 | `postMessage` → `resolve` | `call_soon_threadsafe` → `set_result` |
| 等待结果 | `await promise` | `await future` |

### 主线程拿到 GIL 后事件循环做什么？

```
主线程拿到 GIL 后，事件循环开始一轮轮询：

  ① 检查就绪队列：有没有可以执行的协程？
     → 有：执行该协程直到它遇到 await → 检查下一个

  ② 检查 I/O 回调：有没有网络请求/文件读取完成了？
     → 有：唤醒对应的协程，放入就绪队列

  ③ 检查完成通知：有没有后台线程（run_in_executor）完成了？
     → 有：唤醒等待这个结果的协程

  ④ 回到 ①

  持续执行，直到：
    - 5ms 到了，被迫让出 GIL（后台线程有机会执行）
    - 或者所有协程都在 await，事件循环空闲，主动让出 GIL
```

### 完整时间线示例

以一个主线程 + 2个后台线程的场景为例：

```
时间线 →→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→→

主线程(事件循环):
  [拿GIL] → 跑协程A → 协程A await → 跑协程B → 协程B await
  → 没活了,让出GIL → [等] → [拿GIL] → 发现后台线程A完成了
  → 唤醒等待结果的协程 → 协程继续执行 → ...

后台线程A(PDF解析):
  [等GIL] → [拿GIL,执行Python代码] → [调用PyMuPDF(C扩展),释放GIL]
  → [GIL释放了,C代码继续跑,与主线程真正并行！]
  → [C代码完成,重新拿GIL] → [设置Future结果,通知事件循环] → 线程结束

后台线程B(文件读取):
  [等GIL] → [拿GIL] → [调用file.read(),释放GIL]
  → [等磁盘,与其他线程并行] → [读完,重新拿GIL] → 线程结束
```

## 8. 决策黄金法则

> [!TIP]
> - 任务跑的时候 **CPU 占用低**，大部分在等网络/API → 用 **协程**
> - 任务调用的库**不支持 async** → 用 **线程池**（`run_in_executor`）丢到后台
> - 任务跑的时候 **CPU 飙满 100%** → 用 **多进程**

```
┌──────────────────────────────────────────────────┐
│            任务瓶颈在哪？                          │
├────────────┬─────────────────┬───────────────────┤
│  等网络/API  │  同步库阻塞       │  CPU 算力不够      │
│  (I/O密集)  │  (不支持async)    │  (计算密集)        │
```
