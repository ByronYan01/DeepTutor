# CI 优化方案3：依赖镜像分层实施计划（仅计划，不改代码）

## 1. 背景与问题

当前后端依赖安装发生在镜像构建流程中，`pip install -r requirements.txt`（参考 `Dockerfile:78-79`）在多架构构建下会重复执行，导致：

- 构建时长波动大，受网络/编译影响明显
- `linux/amd64` 与 `linux/arm64` 均重复执行依赖安装
- 业务代码频繁变更时，依赖层复用收益不足

本计划采用**依赖镜像分层**：将 Python 依赖独立构建并发布为可复用镜像，业务镜像只做应用层组装。

---

## 2. 目标与非目标

### 2.1 目标

1. 在依赖未变化时，业务镜像构建不再重复安装 Python 依赖
2. 降低 Jenkins 多架构构建总时长与波动
3. 提升构建稳定性（弱网/外网受限场景）
4. 建立依赖镜像版本化与可追溯机制

### 2.2 非目标

- 本阶段不改业务代码逻辑
- 本阶段不引入新包管理工具（如改用 poetry/uv）
- 本阶段不做全量 CI 流程重构

---

## 3. 方案概述

### 3.1 分层思路

拆分为两类镜像：

1. **依赖镜像（deps image）**
   - 内容：Python 运行时 + `requirements.txt` 解析后的已安装依赖
   - 更新触发：依赖清单变更、基础镜像变更、安全修复重建

2. **业务镜像（app image）**
   - 内容：应用源码、配置、前端产物、启动脚本
   - 依赖来源：复用 deps image（不再重复安装）

### 3.2 版本命名策略（建议）

依赖镜像 tag 建议包含以下信息：

- Python 主版本（例如 `py311`）
- 基础镜像代号（例如 `bookworm`）
- 依赖哈希（`requirements.txt` + 锁定文件 + 关键构建参数）

示例：

- `harbor.xzinfra.com/xz-deeptutor/deeptutor-python-deps:py311-bookworm-<deps_hash>`

> `deps_hash` 建议至少包含：`requirements.txt` 内容哈希；如存在 `uv.lock/constraints.txt` 也纳入哈希输入。

## 4. 实施步骤（分阶段）

## Phase A：基线确认与治理规则

### A1. 基线采样

- 记录当前构建指标：
  - 总构建时长
  - Python 依赖安装阶段耗时
  - 成功率/失败原因分布
- 按分支（dev/main）分别采样，形成对比基线。

### A2. 依赖变更触发规则定义

- 明确“依赖镜像重建触发条件”：
  - `requirements.txt` 变更
  - Python 基础镜像版本或 digest 变更
  - 安全扫描触发强制重建

### A3. 镜像保留策略定义

- Harbor retention：
  - 保留最近 N 个活跃依赖镜像
  - 按分支/环境设置保留规则
  - 定期清理孤儿 tag

---

## Phase B：依赖镜像构建流程落地

### B1. 依赖镜像流水线拆分

- 新增“依赖镜像构建任务”（可独立触发）
- 流程：
  1) 计算 `deps_hash`
  2) 检查 Harbor 是否已有对应 tag
  3) 不存在才构建并推送；存在则直接复用

### B2. 多架构策略确定

二选一（推荐优先级从高到低）：

1. **原生双节点构建（推荐）**：amd64/arm64 分别在原生节点构建，再合并 manifest
2. **单节点 + qemu 构建**：依赖较强环境稳定性，需保障 binfmt/qemu 完整

### B3. 制品可追溯

- 在业务镜像标签、构建日志中记录：
  - 使用的 `deps_image` tag
  - `deps_hash`
  - 依赖镜像构建来源流水线编号

---

## Phase C：业务镜像接入复用

### C1. 业务镜像改造点（仅计划，不执行）

- 业务镜像构建阶段通过参数引用 deps image
- 保持现有前端构建流程不变
- 保持现有启动脚本、supervisor 编排不变

### C2. 回退开关设计

- 增加构建参数开关：
  - `USE_DEPS_IMAGE=true/false`
- 当依赖镜像异常时，可一键回退到原安装流程

---

## Phase D：验证与灰度

### D1. 功能一致性验证

- API 启动、核心接口可用性
- 前端联通后端
- 与当前生产镜像对比行为一致

### D2. 性能收益验证

- 对比指标：
  - 总构建时长下降比例
  - Python 阶段耗时下降比例
  - 构建稳定性（失败率）

### D3. 灰度发布策略

- 先在 `dev` 分支启用
- 通过后再扩展至主干分支与正式发布流程

---

## 5. 风险与应对

1. **哈希维度不足导致复用脏缓存**
   - 应对：将基础镜像 digest、关键锁文件纳入 `deps_hash`

2. **多架构依赖不一致**
   - 应对：强制按架构构建并验证；manifest 合并前做基础 smoke test

3. **Harbor 存储增长**
   - 应对：设置 retention + 定期清理 + 按环境分仓

4. **依赖镜像安全风险**
   - 应对：纳入漏洞扫描；高危漏洞触发强制重建

5. **回归问题影响交付**
   - 应对：保留回退开关，失败时恢复原流程

---

## 6. 验收标准（DoD）

满足以下条件即视为方案落地：

1. 依赖未变更时，业务镜像构建不再执行 Python 全量安装
2. 依赖变更时，可自动触发新 deps image 构建并被业务镜像正确引用
3. 多架构镜像产物可正常推送并可运行
4. 构建日志可追溯到具体 `deps_hash` 与 deps image
5. 出现异常时可通过开关回退到原流程
