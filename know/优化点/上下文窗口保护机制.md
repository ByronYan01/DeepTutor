# 上下文窗口保护机制

> 当前项目没有对 LLM 输入总 token 做整体检查，存在超限风险

---

## 问题描述

每次调用 LLM 时，输入由多部分组成：

```
system_prompt      (~500 tokens)
+ context(RAG)     (不确定，取决于 chunk 数量和长度)
+ history          (最多 4000 tokens)
+ user_message     (不确定)
+ 预留输出空间      (max_tokens 4096)
─────────────────
= 总计可能超过模型的 context window
```

如果 RAG 返回内容很长或用户消息很长，总 token 数可能超过模型上下文窗口限制，导致 API 报错 `context_length_exceeded`。

## 现有的间接控制

| 控制点 | 机制 | 限制的部分 |
|--------|------|-----------|
| `ChatAgent.truncate_history()` | 历史对话最多 4000 tokens | 对话历史 |
| RAG `similarity_top_k=5` | 最多返回 5 个 chunk | RAG 参考内容 |
| `max_tokens=4096` | 限制输出长度，不限输入 | 模型回答 |

**缺失**：没有一个地方把所有部分加起来检查是否超限。

## 为什么目前没出问题

- 主流模型上下文窗口大（GPT-4o 128K、Qwen 128K）
- 短文档 chunk 通常几百 token，5 个加起来几千
- 历史对话已限制 4000 tokens

## 建议优化方案

在 `build_messages()` 最后增加总 token 检查和自动裁剪：

```python
def build_messages(self, message, history, context):
    messages = [...]  # 现有逻辑

    # 新增：总 token 检查
    total = sum(self.count_tokens(m["content"]) for m in messages)
    model_limit = get_context_window(self.get_model())  # 如 128000
    reserved_output = self.get_max_tokens()              # 如 4096

    if total + reserved_output > model_limit:
        # 按优先级裁剪：先砍 history → 再砍 context → 最后砍 user message
        pass

    return messages
```

## 涉及文件

- `src/agents/chat/chat_agent.py` — `build_messages()`
- `src/agents/base_agent.py` — `call_llm()` / `stream_llm()`
- 其他所有 Agent 的 prompt 组装逻辑
